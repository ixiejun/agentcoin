# ac-consensus-bft

AC-BFT：AgentCoin 的抗量子终局性工具（方案 §4.1）。验证人对 Aura-PQ 产出的区块做两阶段投票，每条消息都用自己的 ML-DSA-65 密钥签名（上下文 `agentcoin/bft-vote/v1`）；当权重超过授权节点集合 2/3 的 commit 票达成一致时，最终确定该区块。由此得到的终局性证明，任何人都可以用 `ac_primitives::ac_bft::verify_finality_proof` 验证。

## 协议

设集合有 `n` 个成员、总权重为 `W`，证书需要的权重为 `q = ⌊2W/3⌋ + 1`；集合最多容忍 `W − q` 的故障权重（4 个成员中容忍 1 个）。

1. 第 `r` 轮的领导者（成员 `r mod n`）提议自己的最佳区块：不越过第一个尚未最终确定的集合变更区块，并延伸自己见过的最高 prepare 证书。
2. 成员对满足以下条件的提议投 prepare 票：目标延伸上一个已最终确定的区块，并满足**锁定规则**——没有锁；或目标延伸所锁定的区块；或提议引用了一个轮次更高的 prepare 证书（来自更早的轮次、成员自己见过其全部投票），且目标延伸该证书的区块。
3. 成员在当前轮看到 prepare 证书后，投 commit 票、锁定该证书，并立即进入下一轮，使下一轮的 prepare 阶段与本轮的 commit 阶段并行。
4. commit 证书最终确定其目标及全部祖先。

一轮在两个时隙内没有形成 prepare 证书就超时，超时按 ×1.5 退避，上限 30 秒。收到 `q` 条超时消息，或权重超过 `W − q` 的成员发来更高轮次的消息时，成员进入更高轮次。成员会把让自己进入当前轮的证书转发给仍停在更早轮次的节点，并把自己的最高证书转发给超时消息显示证书较低的节点。每次签名之前，成员都先把要签的内容持久化，因此重启后也不会在同一轮对同一类型签出两条不同的消息。同一成员发出的冲突消息会被作为双签证据举报。

安全性论证写在 `protocol` 模块的 rustdoc 中；`sim` 中的确定性模拟器在 1000 个随机网络上检查安全性和活性（含延迟、丢包、乱序，以及最多 `f` 个静默或双签的拜占庭成员），另有属性测试。

## 模块

| 模块 | 内容 |
|---|---|
| `protocol` | 纯状态机 `Voter`：输入事件，输出动作（`Persist`、`Broadcast`、`Finalize`、`Report`、`Relay`）。不依赖任何节点客户端（`sc-*`）crate，由 `scripts/check-license-boundary.sh` 检查，因此可以供轻客户端和形式化工具复用。 |
| `sim` | 确定性网络模拟器和内存中的区块树（仅用于测试和 `test-utils` feature）。 |
| `network` | `MessageFilter`：通知协议 `/<创世哈希十六进制>/acbft/1` 上消息的验证、去重、轮次窗口和下一集合消息缓冲。 |
| `tracker` | `TrackerState`：各分叉上待生效的授权集合变更，以及应当最终确定某区块的集合；持久化在辅助存储中。 |
| `import` | `AcBftBlockImport`：校验随区块或单独到达的终局性证明，有效则最终确定并保存；为集合变更区块请求证明。 |
| `chain` | 把客户端的区块树作为状态机看到的 `Chain`。 |
| `gadget` | 节点任务：用区块导入、终局性、网络和计时器驱动 `Voter`；先持久化再签名；导出 `acbft_*` 监控指标。 |

## Feature

| Feature | 默认 | 用途 |
|---|---|---|
| `test-utils` | 否 | 向其他 crate 的测试和本 README 的示例公开 `sim`。 |

## 示例

示例代码见英文版 [README.md](README.md)（作为 doctest 运行）：4 个诚实成员在平稳网络上运行 20 秒，每个节点最终确定的高度都不低于 19，且安全性检查通过。

用 `cargo test -p ac-consensus-bft` 运行完整的模拟测试；设置 `AC_BFT_SIM_SEEDS` 可以改变每种网络规模的种子数（默认 334）。
