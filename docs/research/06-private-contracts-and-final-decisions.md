> 状态：讨论稿（Round 6）。日期：2026-09。

## 新增已确认决策

| # | 决策 | 实现注意事项 |
|---|---|---|
| D22 | 社区模型权重完全开源；在本网络推理时，每次付费自动抽取约 5% 分给训练贡献者 | 衍生模型（微调后换了哈希）可以绕过分润，密码学上无法强制。对策：模型注册时声明**血统（lineage）**；声明了血统的衍生模型获得“已验证血统”标识和网关路由优先权，用激励代替强制 |

### 如何让“宪法”真正不可变

Substrate 的 runtime 可以通过治理整体替换，所以**写在 runtime 里的规则，本质上都可以被投票改掉**。要实现真正的不可变，需要把检查放到**节点客户端**层面，也就是 BTC 全节点的模式：

1. **总量上限**：节点在导入每个区块时独立检查 `总发行量 ≤ 21,000,000 ATC`，违反则拒绝该块。即使恶意的 runtime 升级通过了投票，诚实节点也不会接受。想修改这条规则，就必须**硬分叉**，也就是每个节点运营者自愿升级客户端。
2. **无预挖 / 排放规则**：节点校验每个 epoch 的铸币量 ≤ 排放曲线允许的上限。
3. **PoA → PoS 切换**：节点在满足条件时强制执行切换；超过期限仍未切换的区块被拒绝。
4. **协议中立**：这一条无法完全机械化检查，只能靠“runtime 升级内容公开审查 + 社会共识 + 客户端对特定黑名单类存储项的检查”来约束。

## 1. 私有合约有什么意义？

### 1.1 先澄清：公有合约是基础，私有合约只是补充

私有合约不是用来替代公有合约的，两者并存。开发者自由选择：大多数 DApp 用公开的 EVM 合约就够了。问题只在于**哪些场景必须私有，否则根本做不成，或者会伤害用户**。

### 1.2 只有公有合约 + 屏蔽池会出现什么问题

| 问题 | 说明 | 与我们的关系 |
|---|---|---|
| **隐私在合约边界断裂** | 用户在屏蔽池里是匿名的，但一旦和公开合约交互（例如在 DEX 上把 ATC 换成别的资产），金额、时间和对手方就暴露了，攻击者可以反向关联身份 | “天生隐私”只做到了一半 |
| **MEV / 抢跑** | 公开的交易意图会被夹击（sandwich）、抢跑，每年从用户身上抽取的价值规模巨大 | Agent 高频交易时尤其严重 |
| **策略泄露** | Agent 的交易策略、出价、预算全部公开，会被复制或针对 | 我们的核心用户是 Agent |
| **拍卖串通** | 算力采购如果使用公开出价，提供者可以看到彼此的报价并串通 | 大额训练任务的算力采购 |
| **投票贿选和胁迫** | 投票公开，就可以证明“我投了谁”，从而被收买或胁迫 | **D25 的贡献者院和代币投票都需要** |
| **商业机密** | 企业不会把工资、供应链、客户数据放到公开链上 | 企业级 AI 采购 |

### 1.3 私有能力的四个层次

| 层次 | 内容 | 技术 | 成熟度 | 抗量子 |
|---|---|---|---|---|
| **L0** 公有合约 + 屏蔽池 | 私有转账、匿名推理凭证 | STARK 固定电路 | 成熟（Zcash 模式） | ✅（STARK + 哈希） |
| **L1** 协议内置的私有功能 | 私密投票、密封竞价拍卖、屏蔽池内私有兑换、私有算力采购 | 由我们自己编写、一次审计的**固定电路** | 可行 | ✅ |
| **L2** 通用可编程私有合约 | 开发者自己编写私有逻辑 | Aztec / Noir 式：在客户端执行并生成证明 | Aztec 2026 年 Alpha 仍有严重漏洞；需要全新语言和工具链；**Aztec 的证明系统基于 BN254 曲线，不抗量子** | ❌ 需要自研 PQ 证明后端 |
| **L3** 共享私有状态 | 例如储备金隐藏的私有 AMM，多方共同读写同一份加密状态 | FHE / MPC / TEE | 不成熟，性能差 | FHE 可以抗量子，但慢 |

**要点**：
- L1 已经能覆盖我们最需要的场景：Agent 交易、投票、算力采购，并且全部可以用自己控制的 PQ 电路实现。
- L2 的通用性很诱人，但目前没有抗量子的成熟方案，工程量巨大，而且电路漏洞就等于增发漏洞。
- L3 是研究领域。

### 1.4 建议

| 阶段 | 私有能力 |
|---|---|
| MVP | L0：屏蔽池 + 匿名推理凭证 |
| 全量 P2 | L1：**私密投票**（两院制上线的前提）、**密封竞价的算力采购** |
| 全量 P3 | L1：屏蔽池内私有兑换（隐私不再在 DEX 处断裂）；Agent 私有预算与支付 |
| 研究线 | L2：预留 STARK 验证预编译和“私有执行 → 证明 → 公开合约验证”的接口；等 PQ 证明后端和工具链成熟（预计 2028 年以后）再决定是否做通用私有合约 |
| 不做 | L3 |
