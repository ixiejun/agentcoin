# Issue log

Open questions and deviations found during implementation that need tracking: spec wording that needs a decision, acceptance checks done differently from the task text, and follow-ups. Decisions themselves go to [decisions.md](decisions.md); this log only tracks whether each item has been handled and how.

**Status values**: `Awaiting decision` (the user must decide) · `Open` (to be done) · `Handled` (resolved; the plan column says how) · `Closed` (no action needed).

| I-001 | 2026-09-26 | `m2-finality` 7.6; specs consensus/aura-pq "双签被记录" vs consensus/offences "同一违规只记录一次" | The aura-pq Scenario requires a **block-seal** double-signing record on chain, but the offences spec records at most one offence per offender per set. When one key double-signs both blocks and AC-BFT votes, the vote offence may reach the chain first and the seal report is then refused as already decided, so the chain may hold only the vote record. The node test therefore asserts: the seal double signing is detected, its report is accepted or refused as already decided (the runtime has then already accepted the seal evidence), and an offence of alice is on chain. | Handled | Resolved by revising the design instead of the wording (user decision, 2026-09-27): each offence kind is recorded once per offender and set (at most 2 × members records per set), the offender is disabled only on its first record, and the slash handler is told the kinds already recorded so that slashing follows the most severe one without adding up. The aura-pq Scenario keeps its wording and the node test asserts a block-seal offence again. `m2-finality` tasks 9.1–9.4. |
| I-002 | 2026-09-26 | `m2-finality` 7.9; spec consensus/ac-bft "重启后不双签" | A node test cannot inject network messages into a node process, so the task's "after restart, receive a proposal for the same round with a different target" was not tested literally. Instead the validator is killed with `kill -9` after voting and restarted on the same database; every signed message logged before and after the restart is checked, and no (set, round, message type) was ever signed for two targets; finality resumes and no offence is recorded. "Does not vote on the new proposal" is covered by the state-machine unit test `restart_never_signs_conflicting_message`. | Handled (substitute check) | Covered by `node/tests/finality.rs::no_double_vote_after_kill_and_restart` and the protocol unit test. Possible follow-up: a test harness that can inject AC-BFT messages into a node, to test the scenario literally. |
| I-003 | 2026-09-26 | `m2-finality` 8.4; spec consensus/aura-pq "纪元边界后按新列表出块" | Once alice is removed from the set her nodes no longer consider themselves slot owners and author nothing, so there is no block of hers for the others to reject. The e2e test instead checks that at the boundary block both the Aura-PQ authority list and the validator set exclude alice, and that the other three nodes keep producing and finalizing blocks. The "author not entitled" rejection path is covered by the M1 verifier unit tests. | Handled (substitute check) | Covered by `tests/e2e/tests/finality.rs::same_key_on_two_nodes_is_reported_and_disabled` plus the M1 verifier tests. Possible follow-up: a test node that keeps authoring with a removed key, to exercise the rejection end to end. |
| I-004 | 2026-09-27 | m3-pos exploration; MVP plan §3.5, §4.1 ("at most 100 validators"), `MAX_AUTHORITIES = 100` in `ac-primitives` | The validator count is capped at 100 because post-quantum signatures are large: an ML-DSA-65 signature is 3309 bytes (Ed25519: 64). AC-BFT sends two separately signed votes (prepare, commit) per round from every validator, so vote traffic and finality proofs grow linearly: at 100 validators about 660 KB/s received per node and about 230 KB per finality proof; at 1000 about 6.6 MB/s and 2.3 MB. The cap limits decentralization. | Open (deferred by user decision, 2026-09-27) | Options, which combine: (1) one signature per round covering commit(r) and prepare(r+1) — about x2, AC-BFT message v2 and re-verification of the protocol; (2) finality rounds every 2-3 s instead of every block — about x2-3, finality latency about 4-6 s; (3) FN-DSA-512 consensus keys (about 666-byte signatures, AlgId `0x20` already reserved, switch by key rotation without a hard fork) — about x5, only once FIPS 206 is final and a reviewed implementation with official vectors exists (red line 9), security level 1; (4) STARK aggregation of hash-based signatures (full plan P4) — proof size independent of the validator count; (5) random committee sampling — rejected at this scale (a 100-seat committee is stalled by a 25% adversary in about 2% of epochs, and our commit-reveal randomness is biasable). (1)+(2) as a separate change (`acbft-v2`) could raise the cap to about 500. Meanwhile `m3-pos` must not hard-code 100: the active set size K is a parameter and storage bounds leave headroom (for example 1000), so raising the cap needs no storage migration. |

The two specs still say 2,000 and need their wording amended when the change is archived. Raising the cap later needs a multi-block or off-chain election (non-goal of `m3-pos`) or cheaper balancing. |
